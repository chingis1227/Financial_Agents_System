# PRD: НАПОМИНАНИЕ

## Назначение документа

Этот документ фиксирует обязательное напоминание на финальный этап работы над системой. После того как основная реализация будет завершена, необходимо отдельно пройти полный цикл проверки, очистки, ревью, декомпозиции задач и тестирования всей системы.

## Когда выполнять

Выполнить после завершения всех основных работ по агентам, скиллам, PRD-документам, архитектуре и вспомогательным материалам системы.

## Обязательные финальные действия

### 1. Аудит всех документов

Провести полный аудит всех документов системы и закрыть все обнаруженные дыры:

- неполные разделы;
- устаревшие формулировки;
- неописанные сценарии;
- слабые места в логике;
- отсутствующие ограничения;
- неоднозначные требования;
- незакрытые вопросы;
- несвязанные или неиспользуемые документы.

### 2. Проверка несостыковок, дублей и противоречий

Проверить всю систему целиком: агентов, скиллы, PRD, архитектурные документы, методологии и вспомогательные файлы.

Нужно найти и исправить:

- несостыковки между агентами;
- пересечения между скиллами;
- дубликаты функций;
- повторяющиеся требования;
- противоречия в логике работы;
- разные названия для одной и той же сущности;
- конфликтующие инструкции;
- лишние или устаревшие компоненты;
- пробелы между ролями агентов и скиллов.

### 3. Ревью всех PRD-документов

Сделать отдельное ревью всех PRD-файлов:

- проверить полноту требований;
- проверить структуру каждого PRD;
- проверить соответствие PRD общей архитектуре системы;
- убрать повторы;
- привести терминологию к единому стилю;
- убедиться, что каждый PRD можно использовать для дальнейшей реализации;
- отметить, какие PRD нужно переписать, объединить, разделить или удалить.

### 4. Разбить работу на `tasks.md`

После ревью документов и системы нужно разложить оставшуюся работу в отдельный `tasks.md`.

В `tasks.md` должны быть:

- конкретные задачи;
- приоритеты;
- зависимости между задачами;
- критерии готовности;
- список документов, которые нужно обновить;
- список компонентов, которые нужно протестировать;
- отдельный блок для критических исправлений;
- отдельный блок для улучшений, которые можно сделать позже.

### 5. Прогнать систему на реальных запросах

Проверить всю систему на практических сценариях, а не только на теоретических требованиях.

Нужно подготовить и выполнить набор реальных запросов, например:

- запрос на анализ компании;
- запрос на анализ отрасли;
- запрос на рыночную сводку;
- запрос на поиск структурных победителей;
- запрос на анализ финансовой отчетности;
- запрос на работу нескольких агентов вместе;
- запрос с неполными данными;
- запрос с противоречивыми вводными;
- запрос, где нужно выбрать правильного агента или скилл.

По каждому тесту нужно зафиксировать:

- что было запрошено;
- какой агент или скилл сработал;
- какой результат получился;
- где система ошиблась;
- что нужно исправить;
- какие документы нужно обновить.

### 6. Проверить edge cases

Отдельно пройти крайние и нестандартные случаи.

Проверить сценарии, где:

- входные данные неполные;
- пользователь формулирует запрос неоднозначно;
- запрос относится сразу к нескольким агентам;
- агенту не хватает данных;
- данные конфликтуют между собой;
- задача выходит за рамки одного скилла;
- есть риск галлюцинаций;
- система должна отказаться от ответа или запросить уточнение;
- есть пересечение между несколькими PRD;
- есть конфликт между старой и новой логикой;
- результат выглядит уверенно, но основан на слабых данных.

### 7. Продумать режим вопросов после прогона всех агентов

После того как все агенты будут прогнаны и сформируют свои отчеты, нужно отдельно продумать пользовательский режим последующих вопросов к результатам.

Идея: если после полного прогона системы у пользователя появятся дополнительные вопросы, он должен иметь возможность задавать их уже поверх готовых отчетов, а система должна уметь вытягивать нужную информацию из созданных материалов.

Нужно определить:

- где будут храниться финальные отчеты агентов;
- как система будет находить нужный отчет или фрагмент отчета по вопросу пользователя;
- сможет ли пользователь задавать вопросы по одному отчету, по нескольким отчетам или по всей пачке результатов;
- как система будет ссылаться на конкретные выводы, источники, таблицы, метрики и разделы отчетов;
- как отличать информацию, которая уже есть в отчетах, от информации, которую нужно дополнительно проверить или обновить;
- как показывать пользователю, из какого именно отчета взят ответ;
- как обрабатывать вопросы, если в отчетах недостаточно данных;
- как не допускать выдумывания информации, которой нет в отчетах;
- нужен ли отдельный Q&A-слой, индекс отчетов, база знаний или retrieval-механизм поверх результатов агентов.

Этот режим должен позволять:

- задавать уточняющие вопросы после завершения полного анализа;
- быстро доставать факты, тезисы, риски, драйверы, оценки и выводы из отчетов;
- сравнивать выводы разных агентов между собой;
- просить объяснить, почему система пришла к конкретному выводу;
- проверять, на каких источниках или допущениях основан ответ;
- возвращаться к уже созданным отчетам без повторного полного прогона всех агентов, если это не требуется.

## Ожидаемый результат

После выполнения этого напоминания система должна быть приведена к состоянию, где:

- документы не противоречат друг другу;
- PRD понятны и готовы к реализации;
- агенты и скиллы имеют четкие зоны ответственности;
- дубли и повторы устранены;
- оставшиеся задачи вынесены в `tasks.md`;
- система проверена на реальных запросах;
- edge cases выявлены и задокументированы;
- продуман режим последующих вопросов к отчетам после прогона агентов;
- система умеет вытягивать информацию из уже созданных отчетов и явно показывать, откуда она взята;
- критические дыры закрыты.

## Критерий завершения

Эта финальная проверка считается завершенной только тогда, когда:

- все документы просмотрены;
- все PRD отревьюены;
- найденные противоречия исправлены или явно зафиксированы;
- создан и заполнен `tasks.md`;
- проведены тесты на реальных запросах;
- проведена проверка edge cases;
- описан сценарий Q&A после полного прогона агентов;
- описано, как пользователь сможет задавать вопросы к отчетам и получать ответы на основе уже созданных материалов;
- список оставшихся рисков явно задокументирован.

## Mandatory Final System Architecture Audit Reminder

After the main agent, skill, workflow, and framework design work is completed, the system must go through a final architecture audit before implementation.

The audit must verify the exact operating sequence of the system:

- whether agents run strictly one after another;
- whether some agents run in parallel;
- whether agents can communicate through structured handoffs, challenge requests, or shared report artifacts;
- whether agents can call each other directly or only hand off through workflow orchestration;
- whether direct specialist calls follow the same guardrails as full workflows;
- whether the workflow needs a clearer orchestration layer, agent hierarchy, or agent communication structure.

If the audit shows that the agent structure is unclear, inefficient, duplicated, or weakly connected, the system architecture should be updated before implementation.

The audit must also review every designed agent and skill for minimum completeness:

- clear role and ownership boundaries;
- clear non-ownership boundaries;
- required inputs;
- primary output artifact;
- workflow position;
- direct-call behavior where relevant;
- structured handoff fields;
- evidence and source-quality requirements;
- data freshness requirements;
- anti-hallucination rules;
- prohibited actions and prohibited wording;
- safeguards against unsupported recommendations;
- clear report structure;
- appendix rules for source limits, confidence, and technical caveats;
- consistency with `prd.md`, `system-architecture-map.md`, and related workflow files.

No major implementation work should start until this final architecture audit confirms that the system sequence, agent responsibilities, skill coverage, handoff rules, and safety / evidence standards are coherent.
