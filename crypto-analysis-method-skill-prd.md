# Crypto Analysis Method Skill PRD

## Purpose

This skill defines the repeatable method used by the Crypto Agent to analyze crypto assets, tokens, protocols, and crypto-market regimes.

Primary outputs:

```text
crypto_analysis.md
crypto_market_regime.md
```

## Core Method Sequence

```text
Confirm request
-> verify asset / market scope
-> classify crypto economic type
-> apply investment-grade viability gate
-> refresh required data
-> analyze network / token economics
-> analyze tokenomics and value capture
-> assess market structure and liquidity
-> assess macro / liquidity transmission
-> assess regulation, custody, security, and governance
-> analyze valuation / implied expectations
-> apply relevant overlays
-> build scenario setup
-> run edge-case checks
-> produce specialist verdict
-> define monitoring triggers
-> hand off required downstream work
```

## Step 1 — Confirm User Intent

Classify the request:

- single crypto asset analysis;
- BTC / ETH analysis;
- L1 / L2 / DeFi token analysis;
- stablecoin / RWA / tokenization question;
- crypto ETF underlying analysis;
- corporate crypto treasury impact;
- crypto-linked equity exposure input;
- crypto market regime;
- derivatives / leverage setup;
- regulatory impact;
- on-chain / adoption analysis;
- DeFi / staking / yield economics;
- comparison;
- exposure vehicle tradeoff;
- focused factual query.

Separate:

```text
investment thesis
current setup
market regime
vehicle choice
portfolio role
final action
```

Identify the relevant horizon. If the user does not specify a horizon, use 6-36 months for ordinary crypto investment analysis. For BTC or ETH long-term thesis work, 3-5 years may be appropriate. If the user asks about current entry, today's move, a sharp price change, flows, funding, liquidations, depeg, hack, or regulatory headline, add a Fast-Moving Market Setup overlay and separate current setup from long-term thesis.

## Step 2 — Verify Asset Identity

Confirm where available:

- asset name;
- ticker;
- chain / protocol;
- contract address where relevant;
- native asset vs wrapped asset;
- issuer / foundation / core developer entity where relevant;
- exchange listings;
- market cap;
- fully diluted valuation;
- circulating supply;
- total / max supply;
- token standard;
- official website and documentation;
- protocol / governance forum;
- explorer pages;
- major data-provider identity match.

If identity is unclear, the analysis must be blocked or narrowed.

## Step 3 — Classify Economic Type

Classify the asset into:

- monetary / store-of-value;
- settlement / network cash-flow asset;
- application / protocol token;
- scaling / infrastructure token;
- stablecoin / settlement asset;
- RWA / tokenization-linked exposure;
- wrapped / synthetic asset;
- speculative / weak-value-capture token;
- crypto-linked equity or ETF wrapper requiring handoff.

The classification determines which analysis modules are mandatory.

## Step 4 — Apply Investment-Grade Viability Gate

Check reliable identity, liquidity and volume quality, source quality, tokenomics transparency, value-capture mechanism, roadmap / governance visibility, security and custody risks, regulatory feasibility, and manipulation / fake-volume / rug-pull signals.

If the gate fails, produce a limited or blocked output rather than a normal thesis.

## Step 5 — Refresh Required Data

Use freshness tiers:

### Same-day / near-current when setup matters

- price;
- market cap / FDV;
- trading volume;
- funding rates;
- open interest;
- major liquidations;
- ETF daily flows;
- regulatory headlines;
- major hacks, depegs, outages, or exchange events.

### Daily / recent

- spot vs futures volume;
- exchange reserves / flows;
- ETF AUM and cumulative flows;
- stablecoin supply;
- DeFi TVL;
- DEX / CEX activity;
- on-chain activity;
- BTC dominance;
- ETH/BTC;
- total crypto market capitalization.

### Weekly / monthly acceptable

- protocol fees / revenue;
- developer activity;
- active-address trends;
- transaction trends;
- staking participation;
- validator economics;
- tokenization / RWA adoption;
- roadmap progress.

### Event-driven

- regulation;
- protocol upgrades;
- ETF approvals / filings;
- governance votes;
- token unlocks;
- hacks / exploits;
- corporate treasury purchases;
- exchange listings or delistings.

## Step 6 — Analyze Network Economics / Value Accrual

Do not equate fees with tokenholder value. Separate gross user-paid fees, protocol revenue / retained economics, validator / sequencer / miner economics, burn, staking yield, tokenholder value accrual, treasury economics, emissions, incentives, subsidy dependency, and security budget sustainability.

Core question:

```text
Does network activity create durable economic value for this token?
```

## Step 7 — Test Real Adoption Quality

Assess active users vs active addresses, organic activity vs incentive-driven activity, fee-paying demand vs subsidized usage, recurring usage vs airdrop farming, TVL stickiness vs mercenary liquidity, DEX volume quality vs wash activity, bridge volume vs circular flows, stablecoin settlement vs internal reshuffling, and retention or repeat activity where available.

Core rule:

```text
Growth in activity is not automatically growth in durable demand.
```

## Step 8 — Analyze Tokenomics / Value Capture

For non-BTC assets, review circulating supply, total / max supply, FDV, market cap vs FDV, emissions, inflation, unlock schedule, insider / team / VC / foundation allocation, treasury holdings, staking dilution, token utility, governance rights, gas / collateral / security-budget demand, fee share / burn / buyback / revenue link, and foundation or ecosystem selling risk.

Material unresolved tokenomics issues block a positive specialist verdict.

## Step 9 — Analyze Market Structure and Liquidity

Assess price and volume, exchange quality, CEX vs DEX liquidity, order-book depth where available, spot vs futures confirmation, funding, open interest, basis, liquidations, options signal where available, liquidity concentration, and exchange / counterparty dependence.

This module identifies setup quality and fragility. It must not become a trading-signal engine.

## Step 10 — Analyze Structural Demand / Supply

Review where relevant: spot BTC / ETH ETF flows, ETF cumulative flows and AUM, ETF flow persistence, ETF flows versus issuance or float, corporate crypto treasury accumulation, miner selling, foundation / treasury sales, token unlocks, forced-seller risk, exchange reserve trends, and wrapped-asset or bridge supply issues.

For corporate treasury demand, analyze the impact on the crypto asset, not the full equity investment case.

## Step 11 — Analyze Macro / Liquidity Transmission

Assess crypto-specific sensitivity to real yields, USD, global liquidity, Fed liquidity and policy regime, stablecoin liquidity, Nasdaq / risk-asset correlation, BTC dominance, ETH/BTC, credit and risk appetite, and liquidity beta vs digital-reserve behavior.

Full macro regime analysis belongs to Macro Agent.

## Step 12 — Analyze Regulation

Separate:

### Regulatory Catalyst

Recent bill, CLARITY-style market-structure development, stablecoin bill, filing, court ruling, ETF approval, SEC/CFTC action, enforcement event, or policy change; near-term affected assets; market reaction; and whether the event changes timing or risk premium.

### Regulatory Regime Impact

Securities vs commodities classification, SEC / CFTC jurisdiction, stablecoin framework, staking rules, DeFi liability, custody rules, institutional access, exchange listing / delisting risk, and long-term risk premium.

No legal advice is allowed.

## Step 13 — Analyze Security / Custody / Protocol Risk

Review consensus security, validator / miner concentration, client diversity, upgrade risk, chain halt / outage history, smart-contract audits, exploit history, admin keys, multisig / emergency controls, bridge risk, oracle risk, custody dependencies, ETF custodian where relevant, stablecoin reserve or depeg risk, and governance attack risk.

## Step 14 — Analyze Team / Roadmap / Governance

Review core developers, foundation / company backing, roadmap, delivery record, delays, upgrade history, governance model, treasury governance, developer activity, ecosystem health, founder / small-team dependency, and ability to change economics against tokenholders.

## Step 15 — Apply BTC or ETH Overlay

Use BTC overlay for Bitcoin-like assets and ETH overlay for Ethereum-like assets.

## Step 16 — Apply Conditional Modules

Use only when material:

- DeFi / staking / lending economics;
- stablecoin liquidity / settlement;
- tokenization / RWA reality check;
- derivatives / leverage setup;
- on-chain evidence;
- narrative / sentiment heat;
- historical / cycle context;
- exposure vehicle tradeoff;
- crypto-linked equity exposure mechanics.

## Step 17 — Valuation / Implied Expectations Context

The Crypto Agent may evaluate valuation context but must not issue precise final price targets.

Assess what current price appears to require, relevant valuation anchors, MVRV / realized-cap style metrics where relevant, market cap vs FDV, fees / revenue / value capture where relevant, ETF demand / liquidity dependence, supply pressure, relative setup versus BTC, ETH, or peers, and conditions that would justify or break the current valuation.

## Step 18 — Scenario Setup

Provide qualitative scenarios:

```text
Bull case:
Base case:
Bear case:
Key driver separating the cases:
Evidence that would move toward bull:
Evidence that would move toward bear:
```

No default exact probabilities or price targets.

## Step 19 — Edge Case Checks

Before producing the specialist verdict, check whether the analysis falls into one or more edge cases:

1. Meme / low-float / weak-value-capture token.
2. Strong protocol but weak token value capture.
3. TVL growth driven by subsidies or mercenary liquidity.
4. ETH fees weak but ecosystem activity moving to L2.
5. ETF inflows strong but price not responding.
6. Corporate crypto treasury buyer creating reflexive risk.
7. RWA / tokenization growth without token value accrual.
8. Regulatory clarity benefiting some assets while pressuring others.
9. Hack / exploit followed by price recovery.
10. Stablecoin depeg followed by peg recovery.
11. Low market cap but high FDV / unlock overhang.
12. Whale transfer mistaken for selling.
13. Price rally driven mainly by futures leverage.
14. Liquidity tailwind conflicting with regulatory deterioration.
15. Strong team / roadmap but governance can harm tokenholders.
16. ETF wrapper convenience but lost underlying economics.
17. Crypto-linked equity mistaken for clean crypto exposure.
18. Social narrative hot but evidence weak.
19. Historical cycle looks bullish but market structure changed.
20. User asks for operational staking / lending / pool recommendation.

For each detected edge case, include:

```text
Edge Case Detected:
Why it matters:
Required check:
Effect on specialist verdict:
Required handoff:
```

Edge cases do not automatically block analysis. They affect conclusion strength, required evidence, and downstream handoffs. Decision-grade analysis can be blocked by unverifiable low-float tokens, missing decision-critical tokenomics, weak or absent value capture, stablecoin reserve / redemption uncertainty, unresolved exploit root cause, mostly social-media-based evidence, operational yield requests, crypto-linked equity requests without Equity Agent handoff, or ETF vehicle decisions without ETF Agent handoff.

## Step 21 — Monitoring / Trigger Map

Classify confirmation signals, warning signals, thesis breakers, and reassessment triggers.

End the report with structured handoff fields for Evidence, ETF, Equity, Macro, Market Positioning, Market Sense, News & Catalysts, Risk / Red Team, Portfolio Fit, and Investment Committee.
